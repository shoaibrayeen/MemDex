# Memdex

**A local-first memory optimizer for AI coding assistants.** `v1.0.5-beta`

Memdex turns the large, unstructured memory your AI assistant accumulates —
`MEMORY.md`, `memory/`, `AGENTS.md`, `.claude/`, `.cursor/` — into a small searchable index
backed by organized local files and a local ChromaDB vector store.

The point is context. Instead of loading every note into the model's context
window on every task, your assistant loads a tiny index and retrieves only the
memories it actually needs:

```
MEMORY.md  →  small index  →  semantic retrieval  →  the 2-3 relevant files  →  AI assistant
```

not

```
MEMORY.md  →  everything you have ever written  →  AI assistant
```

- **Local-first** — nothing leaves your machine
- **Offline capable** — no API key, ever
- **No cloud memory, no external database** — ChromaDB runs embedded, in-process
- **Deterministic by default** — same input, same output; an LLM is optional
- **Safe** — backups before every change, `--dry-run` everywhere, `memdex restore`
- **CLI-first** — with an optional local dashboard for the token numbers

## Install

Clone the repository, then run the one-shot installer — it handles everything
else, including fetching the right Python version:

```bash
git clone https://github.com/memdex/memdex.git
cd memdex
./setup.sh
```

That puts a `memdex` command on your PATH (via `~/.local/bin`). If your shell
cannot find it afterwards, run `uv tool update-shell` and open a new terminal.
You can then use `memdex` in any project — you never need to be inside this
repository again.

| Flag | What it does |
| --- | --- |
| `--no-ui` | Install without the dashboard enabled in new projects |
| `--offline` | Default new projects to the offline embedder (no model download) |
| `--prefetch` | Download the embedding model now (~80MB, once) so you are offline-ready |
| `--dev` | Development setup: sync dependencies, run tests and lint |
| `--uninstall` | Remove the CLI (your project data is untouched) |

<details>
<summary>Docker</summary>

```bash
docker build -t memdex .

# run any command against a mounted project
docker run --rm -v "$PWD:/workspace" memdex init --here --yes
docker run --rm -v "$PWD:/workspace" -v memdex-cache:/root/.cache memdex run
docker run --rm -v "$PWD:/workspace" memdex search "why did we choose X?"

# the dashboard (bind 0.0.0.0 inside the container so the host can reach it)
docker run --rm -p 127.0.0.1:7644:7644 -v "$PWD:/workspace" memdex ui --host 0.0.0.0
```

Or with compose — `MEMDEX_PROJECT` points at the repo to index:

```bash
MEMDEX_PROJECT=/path/to/your/repo docker compose up dashboard
MEMDEX_PROJECT=/path/to/your/repo docker compose run --rm memdex run
```

Notes for containers: mount `memdex-cache:/root/.cache` so the one-time
embedding-model download survives across runs; `OPENAI_API_KEY` is passed
through from your shell by compose, never stored; to reach an Ollama running on
the host, set `llm.base_url: http://host.docker.internal:11434/v1`.
</details>

<details>
<summary>Manual installation</summary>

```bash
uv tool install .          # recommended — uv fetches Python 3.12 for you
pipx install .             # needs Python 3.10+ already installed
pip install .              # into the active environment
pip install '.[tokens]'    # add tiktoken for exact token counts
```

Memdex needs Python 3.10 or newer. With `uv` you do not need to install one
yourself.
</details>

## How your AI assistant uses this

Point your assistant at the index and tell it to retrieve rather than load.
Add something like this to your `.claude/CLAUDE.md`, `.cursorrules`, or
equivalent:

> Project memory is indexed by Memdex. Read `MEMORY.md` — it is a small index of
> titles, one-line descriptions and paths. Open only the memory files relevant
> to the current task. To find something by meaning rather than by title, run
> `memdex search "<question>" --top-k 3` and read the files it returns.

That is the whole integration. `MEMORY.md` stays small as the project grows,
because it grows by one line per memory rather than by one section of prose.

## Commands

| Command | What it does |
| --- | --- |
| `memdex init` | Set up Memdex in this project |
| `memdex run` | Discover, optimize, reorganize, index and embed your memory |
| `memdex search "<question>"` | Find memories semantically |
| `memdex compact` | Squeeze duplicates and redundancy out of organized memory |
| `memdex index` | Regenerate `MEMORY.md` and refresh the search index only |
| `memdex refresh` | Re-check memory against code that changed since the last refresh |
| `memdex bootstrap` | Write a first memory from your codebase (needs an LLM) |
| `memdex status` | What Memdex knows about this project |
| `memdex history` | Token savings and activity over time, in the terminal |
| `memdex ui` | The same view as a local dashboard |
| `memdex doctor` | Check that everything is wired up |
| `memdex restore` | Put memory files back the way they were |
| `memdex clean` | Wipe the local database (markdown files are kept) |

Every command that changes anything supports `--dry-run` or asks first.

### `memdex init`

Memdex only works on software projects, so `init` checks first:

```bash
$ cd ~/Movies && memdex init
✗ /Users/you/Movies doesn't look like a code project.
  Memdex organizes the memory files an AI coding assistant keeps for a software
  project (MEMORY.md, memory/, .claude/ …), so it needs a repository to work in.
  Run it from your project root — or pass --force if this really is one.
```

In a monorepo it asks which root you meant:

```
You're inside a larger repository: /work/platform
Initialize Memdex for:
  1  the repository root  (/work/platform)
  2  this directory       (/work/platform/services/api)
Choose [1]:
```

Use `--base` or `--here` to skip the prompt, and `--yes` to accept the default.
Once initialized, every other command works from any subdirectory — Memdex walks
up to find `.memdex/`, the way `git` does.

### `memdex run`

The main command. It discovers memory, parses it into logical units at heading
boundaries, removes duplicates, compresses filler, files each memory under a
category, regenerates the index, and embeds everything locally.

```bash
memdex run --dry-run    # show every proposed change, write nothing
memdex run              # apply (a backup is taken first)
memdex run --llm        # use the optional LLM layer for better titles
```

Re-running is a no-op when nothing changed — same files, same bytes, same IDs,
no re-embedding.

### `memdex search`

```bash
memdex search "database architecture"
memdex search "authentication" --top-k 5
memdex search "event sequencing" --category decisions
```

### `memdex compact`

```bash
$ memdex compact --dry-run

Memory Analysis

  Context now loaded:  740 tokens
  After optimization:  465 tokens
  Reduction:           37.2%
  Memory content:      740 → 740 tokens (0.0% smaller)

  Duplicates:
    1 detected
      · Chroma selection

  Redundant sections:
    0 detected

  Large sections:
    0 detected

  Potentially obsolete:
    1 detected
      · Session storage (deprecated)

  Similar, kept apart:
    0 pair(s)

  Would create:
    13 memory files
    1 memory index

Run without --dry-run to apply.
```

Memories flagged as obsolete are **reported, never deleted** — Memdex does not
decide what you have stopped believing.

### `memdex refresh` — after you pull

Several teams commit to the same repository, and memory written last month can
describe code that changed or vanished since. `memdex refresh` compares the
working tree (pulled commits *and* your uncommitted edits) against the last
refresh's git baseline and reports which memories reference the code that moved:

```
$ git pull && memdex refresh

✓ Compared against a1b2c3d4e5f6 (from 2026-09-12): 7 code changes
! 2 memories reference code that changed:
    · ElasticSearch configuration details — ElasticSearchConfig.java
    · Application entry point — Main.java
! 1 memory cites files that no longer exist:
    · Legacy importer — legacy/importer.py
✓ Memory re-indexed (31 memories · 2 re-embedded)
✓ Baseline advanced to d4e5f6a7b8c9

Run memdex refresh --llm to have the model bring the flagged memories up to date.
```

Deterministically it only *flags* — rewriting what a memory says is never an
automatic edit. With `--llm`, each affected memory is shown the current code and
the model decides per memory: keep it, update it (applied with a backup first,
only to files Memdex generated), or mark it outdated (report-only). Either way
the run ends with a re-index, so memory files teammates edited are re-embedded
too, and the whole thing lands in `memdex history` as a `refresh` event.

The first refresh just records the baseline commit and runs the
dead-reference scan. `--since <rev>` compares against any revision instead, and
`--dry-run` reports without writing. To make it automatic after every pull:

```bash
printf '#!/bin/sh\nmemdex refresh --no-llm\n' > .git/hooks/post-merge && chmod +x .git/hooks/post-merge
```

### When there is no memory yet

If a project has no memory at all, there is nothing to optimize — so Memdex
seeds some, and it has two ways to do it:

**Without any LLM (the default).** Your coding assistant — Claude Code, Cursor,
Codex — already reads this repository, so it can write the memories itself.
`memdex run` (or `memdex bootstrap`) creates a `MEMORY.md` template whose
instructions are addressed to the assistant:

```
! No project memory found in the configured sources.
✓ Created MEMORY.md — a template for your AI assistant to fill

Next, ask your coding assistant (Claude Code, Cursor, Codex, …):

  1  Read MEMORY.md and fill each section with real memories from this codebase
  2  Run memdex run to organize, index and embed them
```

The template's instructions live in HTML comments and its empty sections in
`_(none yet)_` placeholders — both are stripped when Memdex indexes the file, so
scaffolding never becomes memory. Running `memdex run` before the template is
filled just says so; nothing junk gets indexed. No API key, no model config.

**With an LLM (`memdex bootstrap`).** Configure `llm` in `.memdex/config.yaml`
(Ollama, LM Studio, OpenAI) and bootstrap reads a bounded slice of the
repository — READMEs, manifests, a file tree, entry-point heads, within
`llm.bootstrap_context_tokens` — and writes the seed memories directly. Prefer a
high-context model; the more of your project it sees at once, the better.

### `memdex restore` and `memdex clean`

Before any change, Memdex copies every affected file to
`.memdex/backups/<timestamp>/` with a manifest:

```bash
memdex restore            # choose from a list
memdex restore --latest   # undo the last run
```

Restore is itself reversible: it snapshots the current state first.

```bash
memdex clean              # drop the vector index + registry; keep everything else
memdex clean --all        # remove .memdex/ entirely (asks first)
```

`clean` **never touches your markdown**. It clears the database Memdex built and
records that you did so — the activity log survives, so `memdex history` still
shows that the memory was reset and when. Only `--all` removes the log too.

## The dashboard

```bash
memdex ui            # http://127.0.0.1:7644
memdex ui --open     # and open a browser
```

A single read-only page showing token reduction per run, memories by category,
and the full activity log including clean events. It is served from the standard
library with no CDN and no build step, so it works offline like everything else.

Prefer the terminal? `memdex history` shows the same data, and `memdex status`
the same summary. The CLI is never the second-class path:

```

2026-09-19 11:11:22  run         906    465  48.7%        14
2026-09-19 11:12:23  index       744    465  37.5%        14
```

in any project's config.

## Configuration

`.memdex/config.yaml`, created by `memdex init`. Every key is optional except
`version`.

```yaml
version: 1

memory:
  sources:
    - MEMORY.md
    - memory/
    - .memory/
    - {path: CLAUDE.md, mode: readonly}
    - {path: AGENTS.md, mode: readonly}
    - {path: .claude/, mode: readonly}
    - {path: .cursor/, mode: readonly}

  output:
    index: MEMORY.md      # the small index an assistant loads first
    directory: memory/    # where the actual memory files live

embedding:
  provider: local         # local | hash | ollama
  model: default

vector_store:
  provider: chromadb
  path: .memdex/chroma

optimizer:
  mode: deterministic     # deterministic | llm
  duplicate_similarity: 0.85
  max_file_tokens: 1200
  min_unit_tokens: 20

llm:
  enabled: false
  provider: ollama        # ollama | lmstudio | openai | openai-compatible
  model: null
  base_url: null          # defaults per provider (openai → https://api.openai.com/v1)
  api_key_env: null       # NAME of the env var holding the key, never the key
  timeout: 30
  bootstrap_context_tokens: 24000

ui:
  enabled: true
  port: 7644
  host: 127.0.0.1         # 0.0.0.0 to reach it from outside (e.g. Docker)

audit:
  enabled: true
```

**Managed vs readonly sources.** A managed source is one Memdex may reorganize
(always after a backup). A `readonly` source is indexed and searchable but never
written to — which is what you want for `.claude/` and `.cursor/`, where the
files are instructions to a tool rather than notes you own. When the same memory
appears in both, the managed copy wins and the readonly twin is left alone.

Memdex only reads the locations you configure. It never sweeps every markdown
file in your repository, because a README is documentation, not memory.

## Embeddings and offline use

| Provider | What it is | Needs network |
| --- | --- | --- |
| `local` (default) | MiniLM-L6-v2 via ONNX, bundled with ChromaDB | Once, ~80MB, then never |
| `hash` | Deterministic feature hashing, pure standard library | Never |
| `ollama` | A local Ollama embedding model | No (localhost) |

For an air-gapped machine, install with `./setup.sh --offline` (or set
`embedding.provider: hash`). Retrieval quality is lower than a trained model's,
but everything works with no download at all.

If the local model cannot be loaded, Memdex warns and falls back to `hash`
rather than failing the run — your files are the product, and the index can
always be rebuilt later with `memdex index`.

**Token counts.** With `tiktoken` installed (the `tokens` extra) counts are
exact. Without it — or when tiktoken is installed but its data is not cached and
the machine is offline — Memdex falls back to an estimate and labels every
number `(estimated)`.

## The optional LLM layer

Memdex works fully without an LLM. When one is configured it can improve titles,
descriptions, categories and merge decisions:

```bash
memdex run --llm
```

<details>
<summary>Ollama</summary>

```bash
ollama pull qwen2.5:14b
```

```yaml
llm:
  enabled: true
  provider: ollama
  model: qwen2.5:14b
```
</details>

<details>
<summary>LM Studio</summary>

Start the local server, then:

```yaml
llm:
  enabled: true
  provider: lmstudio
  model: your-loaded-model
```
</details>

<details>
<summary>OpenAI</summary>

```yaml
llm:
  enabled: true
  provider: openai
  model: gpt-4o            # or gpt-4o-mini
  api_key_env: OPENAI_API_KEY   # the NAME of the env var — never the key itself
```

```bash
export OPENAI_API_KEY=sk-…    # in your shell, .env, or secret manager
memdex run --llm
```

Memdex reads the key from the environment at call time and sends it only as the
request's Authorization header. A key pasted into config.yaml is rejected at
load time. Because the endpoint is remote, every LLM command prints a warning
that memory content will be sent to it.
</details>

<details>
<summary>Any OpenAI-compatible endpoint</summary>

```yaml
llm:
  enabled: true
  provider: openai-compatible
  model: your-model
  base_url: http://localhost:8080/v1
```
</details>

Two rules govern this layer. It runs **after** the deterministic optimizer and
may only relabel memories and confirm or veto merges the deterministic pass
already proposed — it never rewrites the body of a memory and never invents a
merge of its own. And every failure (unreachable, slow, malformed, out of
contract) is a warning, not an error: the deterministic result stands and the
command succeeds.

In default mode — `llm.enabled: false`, a local embedder — **no memory content
leaves your machine**. ChromaDB telemetry is disabled, and the only network call
Memdex can make is the one-time model download, which carries no content. There
is a test that enforces this by making sockets raise during a full run.

## How it works

```
 memory sources (MEMORY.md, memory/, .claude/ …)
        │  discovery — only configured locations
        ▼
 markdown parsing — fence-aware heading tree
        │
        ▼
 memory units — split at headings, never mid-paragraph
        │
        ├── deduplication (exact + near, code-aware)
        ├── compression   (filler only; meaning never changes)
        ├── categorization + importance
        └── stable IDs    (mem_a8f31c, survives moves and edits)
        │
        ├──────────────► memory/<category>/<topic>.md   the knowledge
        ├──────────────► MEMORY.md                      the index
        └──────────────► local embeddings → ChromaDB    the retrieval layer
```

```
src/memdex/
├── cli.py          command surface
├── project.py      is this a code repo? where is its root?
├── config.py       .memdex/config.yaml
├── discovery.py    finding memory files
├── parsing.py      frontmatter + fence-aware heading tree
├── optimize/       structure · dedupe · categorize · compress · deterministic · llm
├── identity.py     hashes, slugs, stable IDs, the registry
├── layout.py       planning the memory tree on disk
├── indexdoc.py     rendering MEMORY.md
├── embed/          local (ONNX) · hash (offline) · ollama
├── store.py        the only module that imports chromadb
├── audit.py        the activity log
├── backup.py       backups and restore
├── pipeline.py     plan (pure) → apply (side effects)
├── bootstrap.py    generating a first memory from code
├── tokens.py       tiktoken or a labelled estimate
├── output.py       all terminal rendering
└── ui/             the local dashboard (standard library only)
```

Two design choices are worth calling out.

**Plan and apply are separate.** `build_plan` reads files and computes
everything — the new tree, the index, the diff, the token numbers — without
touching disk or opening the vector store. That is what makes `--dry-run`
trustworthy rather than a best-effort preview.

**Re-running is a no-op by construction.** Generated files carry no timestamps,
paths are pure functions of category and title, compression is a fixed point,
and the diff compares rendered bytes against what is on disk. A second
`memdex run` writes nothing, takes no backup, and re-embeds nothing.

### Why Python, not Go

The specification asked for Go, and for a local ChromaDB. Those two requirements
conflict: ChromaDB's embedded persistent client and its bundled local embedding
model are Python libraries. A Go build would have to run and supervise a separate
`chroma` server process and find another route to local embeddings — more moving
parts, a weaker offline story, and harder cross-platform distribution, in
exchange for a single binary. Python keeps the database embedded and the whole
thing genuinely offline. `uv` makes installation a one-liner and fetches the
right interpreter, so the practical difference for users is small.

## Development

```bash
./setup.sh --dev      # sync dependencies, run the tests, lint
uv run pytest         # the whole suite — offline, ~10s
uv run ruff check .
```

The suite is fully offline: the downloading embedder is stubbed out so a stray
network call fails loudly, and every fixture uses the `hash` provider. It covers
the parser's fence and frontmatter edge cases, ID stability across moves and
edits, re-run idempotency at the byte level, dry-run making no writes at all,
backup and restore round-trips, clean keeping the audit log, every LLM failure
mode against mocked HTTP, and the no-network guarantee.

## Troubleshooting

**`memdex doctor` first** — it checks the config, the vector store, the
tokenizer, the embedder, the index marker and the LLM endpoint, and tells you
which one is unhappy.

| Symptom | Fix |
| --- | --- |
| `memdex: command not found` | `uv tool update-shell`, then open a new terminal |
| The model download fails | Use `embedding.provider: hash` — fully offline, no download |
| Token counts say `(estimated)` | Install the extra: `uv tool install '.[tokens]'` |
| `Could not open the local vector store` | Needs SQLite ≥ 3.35; on older Linux, `pip install pysqlite3-binary` |
| `memdex ui` says the port is in use | `memdex ui --port 8080` |
| `MEMORY.md still contains your own notes` | Run `memdex run` first; `memdex index` only regenerates the index |
| Another Memdex process is working | Delete `.memdex/lock` if a previous run crashed |
| Search results look wrong after a config change | `memdex index` rebuilds the vectors |

## Versioning

Memdex follows semantic versioning; the current release is **v1.0.5-beta**
(package metadata: `1.0.5b0`). Beta means the CLI surface and config schema are
settling.

**Every change ships a patch bump**, in the same commit as the change and its
[changelog.html](changelog.html) entry:

```bash
python scripts/bump_version.py          # 1.0.1-beta -> 1.0.2-beta
```

Minor and major releases are a deliberate decision, so the script refuses them
unless you say so explicitly:

```bash
python scripts/bump_version.py minor --confirm
python scripts/bump_version.py major --confirm
```

One command updates `src/memdex/__init__.py`, `pyproject.toml`, the Dockerfile
label and this README; a unit test keeps the display form (`x.y.z-beta`) and the
PEP 440 form (`x.y.zb0`) pointing at the same release.
